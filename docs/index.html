Review what your coding agent actually did.

Your agent wrote four hundred lines while you were in a meeting. msr reads the git history that is already there and turns any part of it into a review you can actually read — the change told as a story, beside the real diffs, with a local model explaining what each piece is for. It watches. It never writes back to your code.

Install

Two things: the reviewer, and a local model for the prose. The second is optional — without it you still get grouping, flags, diffs and the review log, just no sentences.

1

Install msr

macOS 
$ brew install mondial7/tap/mondspace-reviewer

Homebrew is the way in on macOS: the cask strips the quarantine attribute during install, before the binary is ever run. That ordering matters — macOS caches its refusal per path, so a download opened first stays refused. Elsewhere, or if you prefer Go: go install github.com/mondial7/mondspace-reviewer/cmd/mondspace-reviewer@latest

2

Install a local model

the reviewer's assistant 
$ brew install llama.cpp

$ llama-server -hf bartowski/Qwen_Qwen3-4B-Instruct-2507-GGUF:Q6_K \
    --host 127.0.0.1 --port 8081 -c 32768 -fa on \
    --cache-type-k q8_0 --cache-type-v q8_0 --jinja
# ~3.3 GB, downloaded once. Leave it running.

That is the whole setup — msr looks for it at 127.0.0.1:8081 by default. Any OpenAI-compatible server works instead; point msr at it on the settings page, or with --summarizer-url.

3

Open a repository

no configuration, no database, no account 
$ cd ~/your-project
$ msr web
reviewing live "Live · uncommitted work" — http://127.0.0.1:7777

It opens on the newest thing worth reviewing. There is nothing to record first — it reads the git history that is already there. It binds to localhost and refuses anything wider without --allow-remote: msr serves your source with no authentication, so putting it on a network should be a decision, not a typo.

How much memory? The 4B at Q6_K needs roughly 4–5 GB resident with a 32k context, so it is comfortable on 16 GB and easy on 32 GB. Running a second larger model alongside it is measurably not worth it: on a 24 GB machine that made every call about four times slower, and the bigger model was less reliable on the hardest request. One model, all three jobs.

Your first five minutes

A short tour of the page. The same tour is built into the app — press ? then take the tour, or open /tutorial.

1

Pick what to review

Top left. Type a tag, a commit, a branch — or leave it on live, which is your working tree against HEAD and where msr opens. Anything in git is reviewable: a commit, a tag (everything since the previous one), a pull request, an agent session, or any two points compared.

2

Ask the assistant to read it

Hit start review on the card at the top. It groups the files by folder, writes one sentence about what each group is for, and tells the change as two to five chapters. Takes about seven seconds locally. Everything below it works with or without that.

3

Read, then annotate

Click a filename for its diff, then click any changed line to write a note about that line — it is anchored to the line's text, so it survives the diff growing above it. j and k walk the files without the mouse. Every note takes one of ok · question · objection · debt · note. That log is the thing you are producing; the prose exists to help you produce it.

4

Finish it

Mark this reviewed, with a closing comment if you have one. Reopening tomorrow says so, and the picker ticks what is done. If the code moved after you signed off, it tells you that too rather than reading as current. Then take the log with you — markdown, JSON or a Slack message — from the card you made it on.

Keys worth knowing

[ previous review
] next review

What you get

Reviewing an agent's work is a specific kind of miserable: the diff is large, it arrives all at once, and the why is buried in a transcript you no longer want to read.

Net change, not keystrokes

One reviewable unit per changed file, so an agent editing the same file eleven times reads as one change — and you can still open the eleven.

Meaning, not filenames

Files that changed together are grouped, and each group gets one sentence about what it is for. "edited jsonl.go" is never shown: the filename already said that.

stated vs inferred vs reported

Three classes, three colours. The agent's own words; a model's guess; and what a deterministic analyser said. Only the third can be acted on without checking it first, and a model can never assert a reason nobody gave.

Flags with no model at all

no-test, new-dep, swallowed-err, public-api, large, todo — offline, instant, and what make you stop. The two that mean stop become findings you can dismiss; the rest are counted once for the whole review instead of repeated on thirty files.

Whatever analysers you already have

golangci-lint, gosec, staticcheck, semgrep, gitleaks, osv-scanner, ruff, eslint — detected on your PATH, run over the files you changed, scoped to the lines your change added. msr ships none of them and says nothing on a machine that has none. Adding one is a block of .msr.toml.

Two engines, one table

Judgement — the story and the two audits — goes to the Claude Code CLI when it is installed; the per-file descriptions stay on your own model, because those are the calls there are hundreds of. Nothing blocks on either, and an answer from the fallback says so rather than borrowing the other's confidence.

Every number is a git fact

Files, lines, commits, tags, pull requests. Nothing on the panel is model-derived, which is rather the point of putting it beside a narration feature.

Nothing you did not ask to hide

A .msrignore keeps generated files out — lockfiles, mocks, vendor/. There are no defaults, because hiding a lockfile by default would mask the one dependency change worth seeing, and what is hidden is always named with the rule that hid it.

The log is searchable

Every note, question, answer and finding across every review in the workspace. "Where did I write that about the retry loop" has an answer.

You are not the only one pushing

A history card shows where you are against everything that has landed, and a branches page shows what everyone else is working on — each row opening a review of exactly that branch's work. Watching the remote is opt-in, because fetching is a network call that writes refs.

Three readings, not one

Story, security, breaking changes — each on demand, each independent. No analysis sees another's findings, because a model shown a previous answer anchors on it. A card is never ambiguous about whether it describes the code on screen, a finding you decide is not a problem stays dismissed, and a rerun re-reads only the files that moved.

One list of checkpoints

Commits, the tags on them and your recorded runs, in one history in time order — with the working tree at the top. Tick two and compare them. It is the only place a checkpoint is chosen, because two controls asking the same question is one too many.

Five themes, and a field that follows them

Auto, light, dark and Solarized both ways. Each column of the isometric field is one changed file, split green over red in the proportion it added to what it took away.

Your agent can ask

msr serves the review over MCP, so the agent that wrote the code can read what you said about it — when it wants to, never interrupted. What you wrote and what a model inferred come through separate calls.

It never writes to your repo

No commits, no branches, no changes to HEAD, the index or your working tree. Snapshots go to their own refs, and comparing against the base is a git archive into a temporary directory rather than a worktree that registers itself. Read-only, by construction.

The model is yours

It runs on your machine, on a port you started. The settings page says whether it is answering, what it has cost, and lets you point msr somewhere else without a restart.

Handing it back to your agent

The point of a review is that the thing being reviewed changes. Until now that meant reading the cockpit and retyping the relevant parts into your agent's prompt.

.mcp.json 
{"mcpServers": {"msr": {"command": "msr", "args": ["mcp"]}}}

Then ask your agent to “check what the reviewer said” and it pulls. There is no hook, no injected message, no file it watches: msr never speaks first, so a working agent is never interrupted with something nobody asked for at a moment nobody chose.

tool
review_statuswhich change is open, whether a human signed it off and what they said, how much is outstanding. Cheap — ask this first
review_feedbackwhat the reviewer is still asking for: questions, objections, debt, in their own words
review_filethe whole human record of one file, approvals included
model_findingswhat msr's audits inferred — behind a name that says so
workspace_feedbackoutstanding feedback across every review. Expensive
workspace_searchfind anything written anywhere in the workspace. Expensive

Human words, and machine guesses, never in one voice

The judge msr runs is a small local model: right often enough to be worth reading, wrong often enough that acting on it unverified is a mistake. So its findings have their own call, every reply opens by disowning human authorship, and each finding names the model and asks to be checked.

Read-only, and it reads the store

No git, no model, no network. Leave it configured — the worst it can do is report what you wrote. Your agent cannot write to the review either: a review log the agent can edit is not a review of the agent.

Watching an agent live

Reviewing git needs nothing. To also capture an agent's stated intent — its own words about why it did something — install the hooks:

optional 
$ msr install-hooks --dir=.

Each hook is an atomic append of one JSON line that exits immediately: your agent runs fine whether or not msr is attached, and attaching later replays the whole log.
